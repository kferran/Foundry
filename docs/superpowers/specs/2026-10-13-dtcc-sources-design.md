# DTCC watcher: mail as a source, and a second watched vendor

**Date:** 2026-10-13
**Status:** Draft for the owner's review.
**Issue:** #140. Amends `2026-10-06-dtcc-change-watcher-design.md` §1 and §11, which put email out of scope.

## 1. Problem

The watcher (`dtcc_run.py`) reads four public DTCC web sources once a day, 30 minutes before the brief. Two misses:
1. DTCC Important Notices and mail from DTCC staff reach the owner's inbox first; one notice arrived by mail a day before the watcher saw it on the web. The repo does not show whether the RSS feed already listed that notice when the mail came: if it did, the gap was the daily cadence and mail buys a day only when the feed lags past the next run.
2. A second vendor, 1035 Yellow Pages, publishes a roadmap and change pages that nobody watches. Nothing in the watcher can take a URL: `dtcc_map.validate` accepts a product only with `page` (a slug appended to the `BASE` constant), `notice_codes` or `api_assets`; `dtcc_fetch.allowed()` rejects every host outside the four-host `HOSTS` constant, and `Run._note()` drops a `source_url` that fails it; the parsers (`page_docs` on `card__title`/`card__date`, `release_block` on "Important Dates" plus `<ul>`, `rss_items` on a notice number in `<title>`, `catalog` on `assetCard`) are DTCC markup; the `dtcc_change` schema's `kind` enum has no generic value, so `dtcc_notes.create` would raise on any other kind.

## 2. Decisions

- **Gap 2 is a small generalisation of the fetcher.** Config alone cannot work (no map key takes a URL, no parser fits another site). A new watcher would copy state, alerts, the flood hold, the note writer, `--brief`, the timer and the skill (about 830 lines per the simplification review). The watcher gets one more source type, "watched page": a `watch:` list in the vault's `map.yaml`, one state bucket, one change rule, one new `kind`.
- **Change rule:** the page's normalised text, as `release_block` already does for the release page (the original spec rejected raw-byte hashing for good reason). Each entry may name an `anchor` regex whose first group is the watched region; without one the whole `<body>` minus `<script>` and `<style>` blocks is watched, which churns on nonces and dates in page chrome. **Owner decision:** the `anchor` for each 1035 Yellow Pages entry. Recommendation: none until two `--dry-run` fetches a day apart show whether the whole page is stable, then anchor what moved. Nobody has fetched those pages from this repo; their structure is unknown here.
- **Gap 1 is one confined Gmail session per run**, on the `triage_fetch.sh` pattern: `search_threads` only, `THREAD_VIEW_MINIMAL`, 50 a page, at most 3 pages, the same deny list of the Gmail server's other tools. The query is `from:<domain> after:<epoch>` (no `in:` restriction, so archived mail counts), the epoch being the start of the last run whose mail step succeeded, minus 300 s, saved in `dtcc_watch_state.json` on that path only (a held or failed step leaves it where it was, as triage advances only on a recorded tick), or 2 days on the first run. The model only searches and replies "done"; the checker reads subjects and snippets from the tool results and ignores the reply. A number is written only when its subject or snippet matches `notice_keywords` (the web path's `dp.matches` rule); an unmatched one is dropped and not recorded in `state["notices"]`, so the web path still judges it. The domain is `mail_domain: '@<dtcc domain>'` in `map.yaml`, validated with `triage.SENDER` like `triage_watch_senders`. The session never writes to Gmail; the usage ceiling (`triage.hold`) applies as it does to triage.
- **Dedupe is the existing key.** The web path writes `key: notice:<number>` and `dtcc_notes.rel_path` derives the file name from the key; `dtcc_notes.create` returns False when the file exists. The mail checker normalises the notice number to the feed's `<title>` form (the fixtures show `a9809` and `24453-26`; the PDF header writes `A #: 9809`) and the mail step writes `notice:<number>` only when that file is absent. The mail subject form is not in the repo: the regex is confirmed against one real notice mail before the step is enabled.
- **The web sources run first, the mail step second, in the same run.** When the feed already lists the notice, the web path writes the full note (PDF header, dates, product codes) and mail finds the file. When it does not, mail writes a thin note (number, subject, thread link, `kind: notice`, `product` absent) and does not mark the number in `state["notices"]`, so the next web run still fetches the PDF, records its dates for `date_conflict`, and skips the note because the file exists. **Owner decision:** keep that thin note (create-once holds, as the schema says) or let the web run fill `deadlines` and `product` into a mail-written note. Recommendation: keep create-once; the thin note is the early signal and the conflict note carries the dates.
- **Staff mail with no notice number needs no code.** `triage_watch_senders` already lists a domain's unread archived mail as `owed` lines, and the inbox query covers mail still in the inbox. **Owner decision:** set `triage_watch_senders: ['@<dtcc domain>']`. Recommendation: yes. The mail step writes notes for notice numbers only; a mail that matches `notice_keywords` without a number is logged in the run line and nothing else.
- **Roadmap fit (Simplify, step 3):** build both in the watcher now; `dtcc_*`, the schema, the skill and the unit move together to the private extension, and the mail step depends only on `lib_connector.sh` and `triage.hold`, which stay in core.

## 3. Changes

- `system/dtcc/map.example.yaml`: `mail_domain: '@<dtcc domain>'` (optional; absent means no mail step) and `watch: [{label: 1035 Yellow Pages roadmap, url: 'https://<vendor host>/<roadmap page>', anchor: '<regex, optional>', notes: ['[[VendorHub]]']}]` (optional). `dtcc_map.validate`: the domain matches `SENDER`; each `url` is https with a host; each `anchor` compiles; `notes` resolve in the partition. `--check` reports these and starts no session, so `smoke_check.sh`'s DTCC line stays offline.
- `dtcc_fetch.allowed()` takes the map's watch hosts in addition to `HOSTS`. `dtcc_parse` gains `watch_text(page, anchor)`, a `text_of` variant that keeps block ends as line breaks.
- `dtcc_run.Run.go()`: a fifth step over `watch` (state bucket `watch`, keyed on URL): first run baselines; empty text or under half the previous length holds the entry (`sanity/watch/<label>`); a changed text writes one note a day per entry, `kind: watched_page`, `key: watch:<label slug>:<date>`, `source_url` the page, Evidence the lines present on one side only (`was:`/`now:`, 20 each at most), Related the entry's `notes`; changes count toward `FLOOD`. Then the mail step: `triage.hold` → `held` with one `[dtcc] mail: held (<reading>)` alert a day; else `subprocess.run(["system/scripts/dtcc_mail.sh", query])`, a non-zero exit → `failed` with one `fetch/mail` alert, as any source. `--dry-run` runs the session and prints the notices it found.
- `system/scripts/dtcc_mail.sh <query>`: `lib_connector.sh` with `CONNECTOR_SERVER="claude.ai Gmail"`, `CONNECTOR_TOOL` the thread search, `CONNECTOR_OTHERS` the deny list copied from `triage_fetch.sh`, `CONNECTOR_TIMEOUT` 300, `CONNECTOR_TURNS` 12; the checker is `dtcc_watch.py --mail-extract <query> < out.jsonl`, which exits with `triage.Fail`'s codes (1, 3, 6, 7) and one `dtcc_watch: <reason>` stderr line for `connector_outcome` to strip; the script prints the checker's JSON and exits `CONNECTOR_EXIT`. The 300 s session fits the service's `TimeoutStartSec=15min`; the unit is unchanged.
- `vaultlib/dtcc_mail.py`: `extract(stream, query, domain)` reuses `triage.pages()` (one tool, the exact query, 3 pages, connector errors), then for each message whose `sender` ends in the domain takes `subject` and `snippet`, finds notice numbers, and returns `{"notices": [{number, subject, thread_id, link, date}]}`; a sender outside the domain is dropped. Mail text reaches a note only through `dtcc_notes.clean`.
- `system/schemas/dtcc_change.md`: `kind` gains `watched_page`. `brief_lines` drops its `DTCC:` prefix for that kind, since the title starts with the entry's `label`. `rel_path` keeps the `dtcc-` file prefix, so a 1035 Yellow Pages note is `dtcc-watch-….md` (a known leak; `_notes()` globs on it).
- `FOUNDRY.md`: the DTCC paragraph names the mail step and watched pages; the inbox triage paragraph points `triage_watch_senders` at vendor domains. `.claude/skills/dtcc-watch/SKILL.md`: `--check` lines for the new keys.

## 4. Tests

- pytest (`test_dtcc_watch.py`, stub streams in the `test_triage.py` shape): a notice in the feed and in mail in one run → one file with PDF evidence; mail first, feed next day → one file, the PDF dates in state, no second note; same input twice writes nothing; a sender outside the domain, a subject with no number, an unnormalisable number and a number whose subject and snippet match no keyword are dropped; a held or failed mail step leaves the `after:` epoch unchanged; another tool, another query or 4 pages → `Fail` 7; the watch entry baselines, then a changed anchored text writes one `watched_page` note with `was:`/`now:` lines, an unchanged text writes nothing, an empty page holds, the brief line carries the label without `DTCC:`; every written note passes the schema; the "no link outside the four DTCC hosts" test becomes "outside the four hosts and the map's watch hosts"; `validate` rejects a non-https `url`, a bad `mail_domain` and an anchor that does not compile.
- bats (`dtcc_watch.bats`, with `triage.bats`'s `gmail_says` stub): a run with `mail_domain` searches once with the built query and nothing else, and writes the note; at the usage ceiling the mail step is held, logged and alerted once while the web sources still run; `--check` with a bad domain exits 2 and starts no session.
- Before the step is enabled on the vault: one `dtcc_watch.py --dry-run` against a real notice mail, which confirms the number regex and the two vendor pages' fetch.

Each fails before the change. Bound tools: pytest, bats and the gate.

## 5. Out of scope

- Smoke-checking the mail session (`dtcc_watch.py --check` stays offline; triage's own check proves the Gmail connector daily when triage is on).
- Full message bodies (`get_thread`), and mail from DTCC that carries no notice number (triage covers it).
- One shared Gmail deny list for `triage_fetch.sh` and `dtcc_mail.sh`; the connector-runner grill dropped the helper layer, so the list is copied.
- Replacing the release page's own hash with a `watch` entry.
