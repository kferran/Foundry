# The Foundry

An Obsidian + Claude Code "second brain" vault template. This file is its manual. A vault's own `README.md` describes that vault (its machines, codebases and what runs where), and template updates never change it (see [Updating and uninstalling](#updating-and-uninstalling)).

> **Status:** in daily use since 2026-10-05 on one Debian server and a laptop client. The headless brief, debrief and intake pipeline passed live acceptance ([record](docs/superpowers/spikes/2026-10-02-plan-4a-acceptance.md)), as did memory capture and recall ([record](docs/superpowers/spikes/2026-10-02-plan-3-acceptance.md)), two-machine sync ([record](docs/superpowers/spikes/2026-10-04-plan-8c-acceptance.md)) and meetings ([record](docs/superpowers/spikes/2026-10-06-plan-11-acceptance.md)). Preferences, style lint and the Foreman orchestrator are still to come (see [Status](#status)).

## What The Foundry is

The Foundry is a template repository that becomes your vault. You clone it, run `claude` inside it, and run `/setup`. Setup configures the vault for your machine, your schedule and your codebases. Nothing specific to a machine or a user is committed. Per-user state is generated at setup time and gitignored.

The vault compiles itself. Raw inputs (files you drop in, plus short digests of your Claude Code sessions) are compiled in batches into a wiki of concepts, entities, summaries and preferences. The wiki is split into `work`, `personal` and `shared` partitions, and links are not allowed to cross between `work` and `personal`. A derived SQLite FTS5 index lets agents ask the index for the notes they need before reading anything, so a lookup reads only the notes that answer it rather than the whole wiki.

Agents follow the writing rules in `CLAUDE.md`: chat replies are sized by type (quick answer, one-screen task report, or a linked document), and notes avoid common AI writing tells. The headless intake, brief and debrief runs edit their own prose against those rules before they publish; `/humanizer` runs the full vendored [humanizer](#acknowledgements) skill interactively.

Automation runs on systemd user timers: isolated headless `claude -p` jobs for intake, a morning brief and an evening debrief, plus a scripted git sync on a server. Headless jobs never write to the vault directly. They write to a staging area, and a deterministic gate validates and publishes their output. Anything that has to be exact (parsing, validation, indexing, unit rendering, git remote handling) is done by a script. The model handles conversation and synthesis.

## How it works

The intended loop is **capture → compile → index → recall → correct**:

1. **Capture.** Files you drop in go to `raw/inbox/`. Intake turns a dropped `.xlsx`, `.docx`, `.pptx` or `.pdf` into text before the redaction every drop gets: a `## Sheet: <name>` table per sheet (the first 1,000 rows, with a line giving the sheet's row count past that; dates stay as Excel's serial numbers), a document's footnotes and comments, each slide with its speaker notes, `## Page N` per PDF page (PDFs need `pdftotext`, from poppler); the original is archived as usual. A file it cannot read (encrypted, corrupt, over 5 MB of text, past the converter's 512 MB and 60 s CPU limits (spreadsheets, documents and slides convert in a child process), holding a DOCTYPE, a PDF with no text layer, no `pdftotext`, or a conversion a crash or kill cut short) moves to quarantine with the reason in its alert. Meeting transcripts go to `meetings/drop/<partition>/` (a server with `meetings_enabled` also fetches Gemini notes from Google Drive); each meeting becomes a meeting note with tracked action items and a searchable transcript. A dropped transcript has no notes, so its meeting note's Summary reads `No summary from the source.` and its other sections `None.` (and its attendees are the speakers its lines name); its facts reach the wiki as concept notes when the meeting is compiled. When the Gemini notes for the same meeting arrive later and the note's Summary, Decisions and Action items are still empty, the import fills each empty section from them and keeps the note's transcript; a section with text in it is never changed. A transcript dropped for a meeting whose note already has content is kept as a second transcript note, linked under that note's title, and the drop is archived. Once the memory hooks are installed, sessions in the vault and in registered codebases also leave short, redacted session digests in `raw/<partition>/notes/` (see [Memory](#memory) below).
2. **Compile.** The intake timer batches up to 5 inputs from one partition into an isolated headless `/ingest` run. For each fact, the run records an explicit noop, patch or create decision and writes its output to `wiki/.staging/<run_id>/`.
3. **Publish.** The publish gate validates schemas and partition walls and rejects changes that shrink existing notes (a removed frontmatter key or heading, or a body cut below 60%). A heading renamed in place passes when its section keeps every non-blank line. It also checks each target against a snapshot taken at the start of the run. If every check passes, it publishes everything at once. If any check fails, it publishes nothing and the run is quarantined. If you edited a note while the run was going, your edit is kept. A note you edited while the gate was renaming is held back, the rest publishes, and the alert names the staged copy under `system/quarantine/<run_id>/staged/`; the gate does not retry it. A rename the filesystem refuses is reported as a failed run, never as a held-back note. The gate refuses any path with a symlink below the vault root on it (the note, its folders, the staging folder, the journal), so a run that writes into a linked folder under `wiki/` or a linked `briefings/` is rejected.
4. **Index.** Markdown is the source of truth. `system/index.db` is a gitignored SQLite FTS5 index that can be rebuilt at any time. Agents run `related`, `query`, `show` and `backlinks` against it before reading any notes.
5. **Recall.** With the memory hooks installed, a `SessionStart` hook adds up to `recall_budget_chars` of vault data (default 9,000 characters, never more than 9,500) to new sessions in scope: the latest digests for the codebase or partition and, once enabled, preferences you have confirmed. A session in the vault itself also gets one line naming the vault's uncommitted files, `N uncommitted files outside raw/` with the first three paths (`raw/`, the other partition's wiki and its meeting drop folder are left out; the line is skipped when git is slow or the index was busy). Recalled text is marked as data, not instructions.
6. **Correct.** Each digest has a Corrections section. Ingest turns these into `preference` notes with linked evidence. A preference's status is calculated in the index, and it becomes confirmed only after you accept it in `/brief`.

**History.** `/backup` first commits each headless run that published files, one commit per run, with a message `commit_runs.py` builds from the run's records (no model writes it). Each carries `Foundry-Command`, `Foundry-Run` and `Foundry-Role` trailers, so `git log` reads as a handoff log: `git log --grep 'Foundry-Command: ingest'` lists the ingest runs.

## Daily use

| Command | What it does |
|---|---|
| `/brief [date]` | The Foreman writes `briefings/<date>.md`. It opens with **Where yesterday landed**: a link to the last debrief of the past 7 days (Friday's on a Monday) and three to five lines drawn from it, then **What changed**: the changelog lines the morning's template update merged, actions first. Then calendar commitments, Before today's meetings (each entity named in today's calendar with its open Now lines and open actions), the Now lines past their decide-by date (Overdue), the open lines of your Now pages (From Now), your open meeting actions, 🎯 Active Projects, a Blockers section (friction, pipeline, communication debt, after any bullet an extension places first, such as telemetry's), ⏳ Waiting on (one brief's worth of everyone else's meeting actions, computed from the import log where meetings are imported and from the notes' own start times elsewhere), and a section from each enabled extension that has one. It adds 3–5 objectives tied to your superpowers and handed to a capability, and the lines an extension section adds (up to 3 newly escalated telemetry groups), to the Now pages. A 🤖 Decided for you section lists each choice the run made that you could have been asked (the option taken, the alternatives, how to reverse it; a question only you can answer is left open there). Counts read `n of N`, and a zero reads `none by HH:MM`. A 📝 Notes section holds your own notes for the day; `/brief` never edits it. Briefings and debriefs from before yesterday move to `briefings/archive/<YYYY-MM>/` |
| `/debrief [date]` | The Foreman writes `briefings/<date>.debrief.md` (embedded in the briefing): a first `signals: N (<date>)` line counting the day's commits, digests, pull requests, alerts and headless runs (its own headless runs count, so a quiet day reads a small number, never 0; a failed git or digest read gives `unknown`), then commits per repo, digest outcomes, headless runs, alerts, what you delivered today, and **Decided for you**: each choice the run made that you could have been asked, with the alternatives and how to reverse it |
| `/ingest <raw file>` | Compiles one raw input into `wiki/`; the intake timer runs it headless in batches |
| `/query <question>` | Answers from compiled `wiki/` notes only, through the index |
| `/lint` | Integrity report plus link, duplicate, contradiction and staleness suggestions |
| `/impact <component> [--repo name]` | Read-only blast-radius table across registered codebases and the wiki |
| `/rca <raw/telemetry/note.md>` | The telemetry extension's skill: root-cause analysis of one production error group, an `rca` note with a Ticket draft, filed only after you tick its Now line |
| `/backup` | Runs the gate (lint, then the test suites when bats and pytest are installed; lint only on a client), commits each headless run on its own, then commits and pushes the rest according to `remote_mode` (through `vault_sync.sh` in `private`) |
| `/order add\|ask\|list\|cancel\|status` | Queues an approved plan (or a task range of one) or a research brief as a Work Order for an unattended run; lists, cancels and reports on queued Work Orders |
| `/setup` | Onboarding; safe to re-run |
| `/humanizer`, `/digest` | Edit prose against the vendored skill; write a session digest on demand |
| `/grilling` | Grill a plan or a new idea, one round of numbered questions at a time, each with a recommended answer; the Foundry adds five questions that validate a new idea (Development) |

**Superpowers** are your strategic anchors, set in `system/config.md` (`superpowers:`). The brief ties each objective to one, and onboarding notes name the ones they serve. They are unrelated to the superpowers Claude Code plugin used in [Development](#development).

**Brief inputs.** The calendar (`calendar.tsv`, from the Google Calendar connector, read 3 events per page so long event descriptions stay under the session's result limit; a page that still exceeds it fails the fetch and the smoke check), `people.md` (the Before today's meetings blocks: each entity note whose title or alias appears in an event title, with its open Now lines and open meeting actions, at most five entities and five lines each), `actions.md` (your open meeting actions, any age, and everyone else's from the meeting notes imported since the previous weekday brief, printed once; none on a weekend), `away.md` (after two or more days in a row before today with no session digest, up to 14, the "While you were away" counts for those days: pull requests merged and still open, Work Orders done and failed, Now lines added and closed, alerts held for the brief, and the Decided for you lines of those days' briefings and debriefs, all dated in the configured timezone; a digest a Work Order wrote does not count as a session), today's and yesterday's alerts, each enabled extension's section (`sections/<name>.md` with its prompt, such as the telemetry extension's production-error groups), `friction.md` (the friction notes no earlier brief has listed, plus a count of all open ones), quarantined inputs, and mail and chat when a Gmail or Slack connector is present in an interactive session. The Sources line (under Unavailable Sources) reads `brief_prep.sh`'s `sources.md`: it counts the sources that are ok and names each one that is not with its failure class, the date it has been failing since (from the smoke check log) and, for an expired login, the credential and how to renew it; outside an interactive session with a mail or chat connector it adds `mail and chat: off`, and Pipeline leaves out alerts that repeat it. Other missing inputs follow on the same line; a source that does not exist yet is omitted, and the brief never fails for one.

**Error telemetry and RCA.** The `telemetry` extension (`extensions/telemetry/extension.md` describes it): an hourly fetch turns each error group from your sources (`system/telemetry/<name>.md`) into a `production_error` note in `raw/telemetry/`, the brief lists them under Blockers, and the `/rca` skill diagnoses one group and drafts a ticket that is filed only after you tick its Now line. It requires the `handoffs` extension, whose site the tickets go to.

**Intraday.** The `intraday` extension (`extensions/intraday/extension.md` describes it) answers what changed since the brief. Every 30 minutes on workdays, `foundry-watch.timer` reads the Slack channels you list in full, your group DMs, your own messages, sent mail, incoming mail and today's calendar, each source in its own confined session. A deadline, a commitment, a review request or a task assigned to you becomes an `owed` Now line, a block that names you a `waiting` line, and a cancelled or moved meeting, an incident or a production alert mail a `[watch]` alert that Slack carries at once. Everything it finds, with the day's session digests and imported meetings, is appended to `briefings/<date>.today.md`, which the briefing embeds under 🕑 Today so far and only the server writes. A capture channel you post to becomes `raw/inbox/` drops the intake compiles. An extension's alert tag can reach Slack at once when its manifest gives it `severity: now` (`alert_tags: [{tag: watch, severity: now}]`); a bare tag waits for the brief. An extension can add a debrief section the same way as a brief section, from its `debrief/` folder.

**Work Orders.** `/order` queues refined work for an unattended run: an approved plan, or a task range of one, or a research brief written with you. Queuing is your approval, and a readiness check refuses items that are not refined enough. `foundry-nightshift.timer` ticks every 15 minutes on a standalone machine or a server (never a client). Up to 3 Work Orders run at once: the tick starts another as one finishes and stays running until none is left to start. Two plan orders on the same repo and base run one after the other. A Work Order starts now unless it was queued for a set time (`--at`) or for the run window (`--window`, the `run_window` setting). By default `run_window` is empty and the window is always open; a vault that sets one, such as `22:00-05:00`, keeps it. Before this update the window defaulted to `22:00-05:00`: if you relied on that, set `run_window: "22:00-05:00"` before updating, or Work Orders already queued for the window start at the next tick. No new Work Order starts while the last session's 5-hour usage is at or above `order_max_five_hour` (default `0.6`) and that reading is under 5 hours old, checked again before each start; a running one carries on, and `/order status` shows the hold. Design sessions (brainstorm, spec, plan) hand an approved plan to the Foreman session, which queues it with `/order add`. Run the Foreman session and your design sessions in the same permission mode, so a handoff is not held for approval. A plan item runs in a private clone under `order_workspace`, is verified, pushed to a branch and ends in a pull request; it never merges or deploys. The sealed verify sees only `/usr/local/bin:/usr/bin:/bin` and nothing under `$HOME`, so a toolchain installed per user (nvm, volta, asdf, `~/.local/bin`) is not found and its command ends with `exit 127 (command not found in the sealed verify sandbox)`. Two optional keys in `system/codebases/<name>.md` open that up: `order_toolchain`, a list of directories (`~` allowed) that hold the toolchain's executables, which the sandbox binds read-only and puts first on its PATH (the rest of `$HOME` stays empty), and which lead the plan session's own PATH too; and `order_install`, one command (such as `pnpm install --frozen-lockfile --ignore-scripts`) that runs once, first, in the same private checkout with the network open, before the verify commands run offline. The install is the only sandboxed step with network, and the branch's lockfile decides what it fetches. Each sandboxed step starts with a fresh, empty `$HOME`, so the install must leave what verify needs inside the checkout: anything it puts under `$HOME` (browser binaries, a package store) is gone by verify. Corepack's downloads are the exception: every sandboxed step of the item gets one `COREPACK_HOME`, writable during the install and read-only during verify, in the item's verify directory outside the checkout, so a pnpm or yarn version pinned in `packageManager` that the install's corepack shim downloads is the one verify runs offline. The install runs from an empty cache every run, under the 30-minute step timeout, and without `--ignore-scripts` the branch's install scripts run with the network open. A failing install blocks the item like a failing check, as `Fix the failing check: order_install: <command>: exit <code>`. A listed directory that is gone when the item starts (an nvm upgrade, an item queued on a client with other paths) blocks it before the session runs, with the same wording queuing uses. List the directories the tools really live in; only those show through the empty `$HOME`, so a symlink into an unlisted directory dangles. For nvm that is `~/.nvm/versions/node/<version>/bin` and its `lib` sibling, since `npm`, `npx` and a globally installed `pnpm` there are symlinks into `../lib`. A shim directory that needs its manager's environment does not work in the sealed sandbox. Queuing refuses a listed directory that does not exist. A research item reads its sources and writes one findings note. Each item runs in a fresh, confined `claude -p` session that reads nothing of the vault, gets eight named environment variables and holds no credential. The session's sandbox and its Read tool deny the vault root, every other registered codebase and the common credential paths (`~/.ssh`, `~/.config/gh`, `~/.gitconfig`, the Claude transcripts under `~/.claude/projects` and its `settings*.json` among them). Its environment is `PATH`, `HOME`, `USER`, `LANG`, `TZ`, `TMPDIR`, `FOUNDRY_CLAUDE_BIN` and `CLAUDE_CONFIG_DIR`, each when set, and nothing else: an agent socket or a token in the unit's environment (`SSH_AUTH_SOCK`, `GH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`) never reaches it, and the daily sandbox self-test fails when one of its probes (`SSH_AUTH_SOCK`, `GH_TOKEN`, `GITHUB_TOKEN`, `DBUS_SESSION_BUS_ADDRESS`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`) does. Everything else is dropped, `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY`, `SSL_CERT_FILE` and `NODE_EXTRA_CA_CERTS` included, so a vault behind a proxy or TLS inspection stops starting sessions, and the self-test's reason carries the session's result text and its last stderr line. A vault whose `claude` is logged in only through `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` therefore starts no Work Order session; the sandbox alert says so, and `claude login` (the credentials file the health check tests) is the login a session can use. After `claude login`, the self-test reruns on the next report day's first tick, or at once with `system/scripts/nightshift.py selftest`. `order_workspace` must sit outside the vault: the clone, a research item's context copy and its `out/` live there, and the session denies the vault root, so `/order add` answers `not ready: order_workspace is inside the vault` and an item already queued fails with a Needs-you line until the workspace moves. The report, `system/logs/nightshift/<date>.md` (heading `# Work Orders: <date>`), starts with a health banner, then "Needs you" (decisions only), which the brief adds to the Now page. Queue notes live in `raw/<partition>/nightshift/`, tracked in your vault so an item queued on a client reaches the server. A plan item for this template is read from `template_remote`: push its branch there before queuing it, and queuing checks the remote, which needs the network and the remote's credentials. Settings renamed with Work Orders: `run_window` was `nightshift_window`, `order_workspace` was `nightshift_workspace`, and a codebase's `order_pr`, `order_hosts` and `order_plugins` were `nightshift_pr`, `nightshift_hosts` and `nightshift_plugins`. The old names still work; rename them when convenient. The command, the skill and printed text say Work Orders; files, units, the queue folders and `nightshift.py` keep their names.

**Session tasks.** A recurring task the Foreman schedules inside its session (an inbound sweep, work for a quiet hour) ends when the session does. The Foreman recreates the tasks listed under `## Session tasks` in `system/agents/foreman.md` at the start of each session, one `- every <interval>: <prompt>` line each. The template ships the list empty; your vault keeps its own lines there, and the daily template update merges around them.

**The usage ceiling.** Every unattended session shares one Claude account's usage window. While the last 5-hour usage reading is at or above `order_max_five_hour` (default `0.6`) and under 5 hours old, intake ingests, the meetings fetch, inbox triage and new Work Orders wait: their inputs stay where they are, the next tick re-reads, and each raises one alert a day. The brief, the debrief and Slack notices never wait, nor does filing an RCA ticket you approved (one short session per ticked line). The reading comes from the session itself: every headless run, brief and debrief included, records the reading its stream reports, as Work Orders do, in `system/logs/nightshift/health-<date>.json`. A run keeps its full stream (`system/logs/runs/<run_id>/stream.jsonl`) only when it failed.

**Smoke check.** `foundry-smoke.timer` runs `smoke_check.sh` 15 minutes before the brief on a standalone machine or a server. It runs every configured fetch's `--check` (calendar always; meetings, inbox triage and chat triage when they are set up; each enabled extension's smoke entries) and compares the `claude` version with `system/logs/claude.version`, then prints one line per source (an extension source checked per item as `<source>/<item>`, such as `telemetry/<name>`): `ok`, `failed: <reason>` or `off`. Every fetch's failure reason starts with its class: `auth`, `network`, `timeout`, `connector`, `claude` or `other`. An `auth` failure, or a `claude` that is logged out, reads `expired: <credential>; renew: <how>` instead, with one alert a day per credential (the Google connector for calendar, meetings and triage; the Slack connector for chat triage; each extension's credentials, named in its manifest; the `claude` login). A `network` failure reads `unreachable: <host>` and alerts once a day when the previous check failed the same way. Any other failing source raises one `[smoke]` alert a day, which the brief lists under Blockers; a `claude` version change reads `changed: <old> -> <new>`, is not a failed source, and raises one `[smoke]` alert naming both versions and the acceptance steps to re-run (the brief lists it under Pipeline; Slack never carries it), then records the new version. It also prints one line per timer this vault installed (#166): `ok` when systemd's last trigger is no older than the timer's next tick plus a grace (one interval, at most 2 hours), `stale: no run since <time>` past that with one `[smoke]` alert a day, `unknown` before the timer's first trigger, `off` when you disabled it. A run that started and failed is in the run ledger, not here. A `units` line compares every unit and drop-in `install_units.sh --dry-run` renders with the installed copy: `ok`, or `differs: <unit>` with one alert a day per unit naming `system/scripts/install_units.sh --update` as the fix; a unit you never installed is left out, and with none installed the line reads `off`. Nothing is fixed or rolled back for you. The checks are logged to `system/logs/smoke-<YYYY-MM>.jsonl`. Slack notices are not checked: `notify.sh --check` posts a real message, so you run it by hand. Each connector check is one short confined session, so the run costs usage once a day; at the usage ceiling the connector checks are held (`held: <reading>`, one alert) and the local checks still run. To stop the daily check, run `systemctl --user disable --now foundry-smoke.timer`; later updates keep it disabled.

**Vault-only extensions.** A vault can keep its own extensions under `extensions/<name>/`, tracked only in the vault's repository and listed in `extensions:` like any other. The template merge never touches a folder the template does not have, and the gate runs a listed extension's tests. A unit an extension ships may run at `{{PRE_BRIEF_TIME}}`, 30 minutes before the brief.

**The Now page.** `wiki/<partition>/Now.md` is one checklist per partition of open loops: what you owe (`owed`), what you wait on (`waiting`) and messages not yet sent (`draft`). Each line is `- [ ] <kind>: <statement>[ [rec:: <option>: <why>]][ [due:: YYYY-MM-DD]] (<who>, since <date>[, <evidence>])`. Sessions add lines with `system/scripts/now.py add`, and the brief adds its new objectives, Work Order decisions, the lines an extension's section asks for, and escalated telemetry groups (with the note path as evidence, which closes nothing: you tick those lines). `rec` is the writer's recommendation (`--rec`) and `due` the date the line should be settled by. Every new line gets a `due`: the `--due` the writer passes, else 3 days after `since` when a person is named (`--who`) or the statement names a date of its own within the next 30 days (a Work Order id, a file name or a date inside a link or a path does not count; a deadline months out keeps 30 days), else 30 days. Adding a line that is already open writes nothing unless it brings something new: an earlier `--due` moves the date earlier, `--rec` sets or replaces the recommendation, and `--evidence` is set when the line has none; a later `--due` is refused (exit 2). You can move a date by hand in Obsidian (Dataview also reads `[due::2026-10-20]` and any case of the key, and `now.py` reads them the same way); a date that is not a real day counts as none. Lines written before this update have no `due` until a writer sets one. The brief's prep runs `system/scripts/now.py overdue` (read-only; `--date` picks the day): the brief prints its output as **Overdue**, just before From Now, listing the open lines past their `due` in groups of 1 to 7, 8 to 30 and more than 30 days over, at most 10 lines (the fewest days over first) and then a count of the rest, and then how many of all open lines have no `due` (`2 of 8 open lines carry no clock.`). A line leaves Overdue only when you tick or drop it, its evidence closes it, or you edit its `due`. The brief's **From Now** block is a Dataview query over both pages: tick a line there (`[x]` done, `[-]` dropped) and the tick lands on the Now page. Every 5 minutes on a standalone machine or a server, the intake timer runs `now.py check`: a line whose evidence is a GitHub pull request that merged or closed, a GitHub issue that closed, or a Work Order that is done, failed or cancelled, is ticked with `_(closed: <how> <date>)_`. A line you tick gets `_(closed: ticked <date>)_` on the page's next write (a line added or closed by evidence), not on a tick of its own, so the server rewrites a page the client edits less often; the stamp can be a day or two later than the tick. At each brief, the prep moves closed lines and their notes to `wiki/<partition>/now-archive/<YYYY-MM>.md` (`now.py archive`, the month of the stamp), so the page holds open lines only. A line keeps a short statement (`add` and `set` refuse a line over 300 characters, and so does the publish gate for a line the brief adds); its history goes under it as dated notes, `  - YYYY-MM-DD: <update>`, with `system/scripts/now.py note --partition <p> --match "<text>" --text "<update>"`. The brief prints no notes. In a lull, the Foreman runs `system/scripts/now.py review --partition <partition>` (read-only: lines closed by their evidence, open more than 14 days with no evidence, duplicated, or unreadable because text or a `[rec::]` or `[due::]` field sits after the parenthesis (`check` skips such a line; recall ranks it by its own fields and `now.py set` can rewrite it), which you move back by hand; also long lines (over 300 characters, which `add` and `set` refuse), and a page over 25 KB; `--stale-days N` moves the threshold) and proposes the closes and merges to you as one batch; it ticks nothing itself. Session recall shows the session partition's open lines first. The first brief after this update creates your default partition's page from the previous brief's open objectives.

**Inbox triage.** With `triage_enabled: true` (`/setup` phase 6b), `foundry-triage.timer` runs `triage_fetch.sh` every 30 minutes on workdays from 08:00 to 18:00 on a standalone machine or a server. A confined `claude -p` session that may only search Gmail reads the inbox since the last tick (promotions, social and forums skipped) and lists the threads that need you: a person asks you something, waits on your answer, or reports a production problem. Each new message in such a thread becomes one `owed` line on the Now page of `triage_partition`, with its mail link, plus one `[triage]` alert line. The links and dates come from the search results, never from the model's words. It reads subjects and snippets, not full bodies. With `triage_watch_senders` set (domains such as `@example.com`, or addresses), each tick also searches those senders' unread mail outside the inbox from the last two days, and lists every such thread: mail archived unread by hand is not missed. It only reads; it never moves mail back to the inbox. With `triage_chat_enabled: true`, each tick also runs a second confined session that may only search Slack: it reads the messages posted since the last tick in only the channels you are a member of (public and private; DMs and bots skipped; at most 100 messages a tick) and lists those that need you the same way, each as an `owed` line with its Slack link. Results in `slack_notify_channel` are skipped, so triage never reads its own notices. A failure in mail or chat does not stop the other. A tick is skipped while the 5-hour usage is at or above `order_max_five_hour`, and a connector failure alerts once a day.

**Slack notices.** With `slack_notify_channel` set (`/setup` phase 6d), `foundry-notify.timer` runs `notify.sh` every 5 minutes on a standalone machine or a server. It sends one message with everything new since the last one: a brief that finished (how many Now lines need you, how many wait, how many alerts today, and a link to the briefing), a debrief that finished (its link), a brief or debrief that failed (its exit status), a Work Order that ended (its id, its state and its pull request, a link to its findings note, or what it needs), and every new alert line whose tag Slack carries (the table below; an alert repeated while a problem lasts goes out once a day, and inbox triage alerts go out as a count, never with mail text). The retries of an input that ends poisoned or quarantined stay in the alerts file, and Slack gets the outcome: `ingest of raw/inbox/<file> failed …; will retry`, `digest <file> failed …; will retry`, `digest batch in <partition> failed …; retrying one at a time`, `meeting import of <file> failed …; will retry`, and the `ingest <run_id>: publish rejected or empty` and `ingest <run_id> failed (exit N)` lines of each attempt. Every other "will retry" line (the Now check, RCA filing, briefing extraction, the meeting import as a whole) goes out once a day while it lasts. A poisoned input goes out as its path, the publish gate's reason (the check and the note, without the detail or any path) and the `system/scripts/intake.py --retry-input <name>` command to run once the cause is fixed; when the line would pass 300 characters the reason is shortened or dropped, never the command. Vault paths standing on their own, run ids and Work Order ids go out as written; the rest of a line, and anything glued to a path, is redacted, and `&`, `<` and `>` are escaped so no name can mention or format in Slack. Links are GitHub file links (none when `origin` is not on github.com); with `notify_links: obsidian` they are `obsidian://open?file=<path>` links. They name no vault, so no vault-name setting is needed; Obsidian's help gives "the current or last focused vault" as the default only for its `hook` action, so with several vaults on one device, check which one a link opens. Whether Slack makes an `obsidian://` link clickable on desktop and mobile has not been tested. With nothing new it starts no session. Otherwise one confined `claude -p` session that may only call the Slack connector's `slack_send_message` posts it. The connector is `slack_connector`, by default `claude.ai Slack` (Slack connected at claude.ai), which is what a headless session loads; when a session finds no Slack tool, `notify.sh` exits 3 and names the Slack server the session did load. A post that did not reach Slack is resent on the next tick, for events up to a day old. A session that breaks its rules (another tool or channel) stops notices until you read the `[notify]` alert and delete the hold file it names. No note text from `wiki/` is sent. Notices are not held at the usage ceiling, and they cannot be sent while the account's usage limit is reached. Empty `slack_notify_channel` turns them off. With `slack_notify_thread: daily` (default `off`), the day's first notice also posts a parent, `Foundry updates <date>`, and that notice and every later one that day (brief, debrief, alerts, Work Orders) go out as replies under it; a quiet day has no parent. The session is handed the thread, and the checker refuses a post with any other channel or thread. Every post's ts, read from the link Slack returns, goes to `system/logs/notify/thread.json` (7 days); a post whose link cannot be read holds notices, so at most one notice goes unrecorded. With threading on, the intraday extension can capture from the same channel: your top-level posts and your replies in these threads become inbox drops (#293).

Each alert line names the part that raised it in brackets. The tag decides where it goes (`system/scripts/vaultlib/alerts.py` holds the table; an untagged line or an unknown tag waits for the brief):

| Tags | Where it goes |
|---|---|
| `foreman`, `incident`, `orders`, `sync`, `update`, `rca`, `intake` | Slack at the next tick |
| `triage` | Slack at the next tick, as a count |
| `commit_runs`, `smoke`, `calendar`, `meetings`, `handoffs`, `telemetry`, `memory`, `extensions` | the next brief |
| `notify` | nowhere (the notifier's own lines) |

An `incident` line is a new production error group, or a resolved one that came back, found by the hourly telemetry fetch in a source whose `environment` starts with `prod`: the source, the service, the error, its event count and its note in `raw/telemetry/`, at most 3 per source per run and once a day per group; a source's first run pushes none. Three tags decide by their text: a `triage` line that is not the new-mail count (a failed triage fetch) waits for the brief, a `smoke` line about a stale timer goes to Slack at once, since a stale brief timer means no brief would show it, and so does a `telemetry` line from the secrets scan (a new group whose log line holds a credential shape, which needs rotating before the brief); other `telemetry` lines wait for the brief. Every line also stays in the day's alerts file, and the brief lists them under Pipeline, grouped by tag. To tell you something now, outside the brief, a session runs `system/scripts/alert.py foreman "<one line>"`; something you owe or wait on stays a Now line. On a client, which runs no notifier and no brief, `alert.py` refuses (exit 3).

**Active Projects.** An optional `wiki/<partition>/ActiveProjects.md` lists your project pages in priority order under `## Active`. Each morning, `active_projects.py` reads those pages, and the brief shows each project's next 3 open checkboxes and the open items under its "Decisions…" heading, as plain bullets. You tick items on the project page, so nothing is tracked twice.

**Meetings fetch: retrying a skipped Doc.** After three failed reads of one Gemini Doc (any non-zero exit, timeouts and usage limits included), the fetch alerts once ("`<id>` failed 3 reads; it is skipped from now on") and skips it, because it counts failures in this month's and last month's `system/logs/meetings_fetch-<YYYY-MM>.jsonl`. To fetch it again: delete that Doc's `"step": "read"` lines from those two log files, then set `system/logs/meetings_fetch.since` to a time before the Doc was created (ISO 8601, UTC), so the next run's search window includes it. The next fetch reads it once more; the `.since` file moves forward again on success. (#44)

**Quarantine.** An inbox file or digest whose ingest fails 3 times (or once with exit 2) moves to `system/quarantine/poisoned/` with an `.origin.json` sidecar. Editing it there does nothing: fix the cause, then run `system/scripts/intake.py --retry-input <name>` to put that one input back where it came from (`--retry <run_id>` restores a run's inputs, `--retry-all` every poisoned input). `system/scripts/intake.py --quarantine` lists everything quarantine holds, one line each with its since date and way out: poisoned inputs, meeting sources (fixed at the source), held-back run staging and corrupt telemetry state backups (both safe to delete). The brief and debrief prep write that list to `system/logs/inputs/<date>/quarantine.md`, and both read it from there, so they agree: the brief's Blockers name each poisoned input with its retry command, and the debrief says what entered and left quarantine that day.

**Debrief inputs.** The prep files in `system/logs/inputs/<date>/` (git commits, session digests, and `orders.md`, the open Work Orders report), alerts, the run ledger `system/logs/runs-<YYYY-MM>.jsonl`, and the telemetry run log `system/logs/telemetry-<YYYY-MM>.jsonl`.

**Delivered work.** Handoffs to chase (stalled tickets you reported that someone else holds) is an extension: each enabled extension's brief section comes from its own `brief/` folder (`/setup` phase 6e). The debrief lists what you delivered under 6. Delivered Today: each digest's Delivered section, `delivered:` lines in the briefing's 📝 Notes (the Foreman adds one when you ask it to log something), and pull requests you opened, merged or reviewed in the registered GitHub repositories (`gh`, logged in; a codebase's `order_pr: github:<owner>/<repo>` and a GitHub `template_remote`).

**Workcells.** Work goes to the Workcell whose `capabilities` include the one the work needs, never by name. The routing rules live in `system/agents/foreman.md`, which `CLAUDE.md` tells every session to read; the approved-plans rule lives in the `order` skill, which loads when you approve a plan:

| Workcell | Capabilities |
|---|---|
| `coding.md` | `code`, `tests`, `refactor` |
| `maintenance.md` | `vault-health`, `dependencies`, `telemetry`, `alerts`; owns `raw/telemetry/` notes, which it checks against local branches of the affected codebase |
| `research.md` | `research`; answers a question within the session, read-only (index first, then named sources and public web pages), and hands the Foreman a findings note draft to file through `/ingest` or `raw/inbox/` |

**Friction.** Ingest sets `is_friction: "true"` when a fact's source text says "not sure", "waiting on", "stuck", "blocked", "tbd" or "double-check". The brief prints each flagged note's name once, the first morning after it is flagged, then counts it: "listed before" is read from the earlier briefings (the Friction part, or the old Friction notes bullet), so the two machines agree without a ledger.

## Memory

Memory is part of The Core. It is optional and off until you install its hooks. `/setup` offers them in its memory step: it shows the change `system/scripts/install_hooks.sh --dry-run` would make to your user-level `~/.claude/settings.json`, explains each entry, and installs only after an explicit yes. Declining leaves memory off; re-run `/setup` to turn it on later.

| Entry | What it does |
|---|---|
| `memory_recall.sh` (`SessionStart`) | Adds recent digests for the codebase or partition to a new session, up to `recall_budget_chars` (default 9,000 characters), marked as vault data, not instructions |
| `memory_capture.sh` (`Stop`) | After enough work (`digest_min_events` tool events and `digest_min_minutes` minutes since the last digest, default 5 and 20), asks for a short digest once, then redacts it and writes it to `raw/<partition>/notes/` |
| `memory_activity.sh` (`PostToolUse`) | Counts edits and Bash calls toward that threshold |
| `memory_keep.sh` (`PreCompact`, `SessionEnd`) | Copies the session's transcript (only one under `~/.claude/projects/`, or `$CLAUDE_CONFIG_DIR/projects/`) to `transcript_keep_dir` (default `$XDG_STATE_HOME/foundry/transcripts`, else `~/.local/state/foundry/transcripts`), mode 600, so a digest the Stop hook missed can be recovered from it. `/`, your home directory, the vault (through a symlink too) and a directory you do not own or others can write to are refused. A directory the hook creates is mode 700 and gets a `.foundry-keep` marker. A copy larger than the transcript is kept as it is; otherwise the copy is replaced atomically. Only in a directory with the marker, it deletes the session-id-named `*.jsonl` copies directly in it not refreshed for `transcript_keep_days` days (default 90; 0 never deletes), never recursing or following a symlink |
| `usage_log.sh` (`UserPromptSubmit`, `PreToolUse` on `Skill`) | In a session whose working directory is the vault root, appends `{ts, command}` for a prompt that starts with a vault command or skill (`/<name>`) or a plugin's `/<plugin>:<name>`, and `{ts, skill}` for each Skill tool call to `system/logs/usage-YYYY-MM.jsonl`. It never logs the prompt text or arguments. Headless runs count their commands in the run ledger |
| three `permissions.allow` rules | Let codebase sessions run `vault_index.py related`, `show` and `backlinks`, which return only that codebase's partition plus `shared` |
| `~/.claude/commands/digest.md` | The `/digest` command, written only if you have no `digest.md` of your own |

The hooks run in every Claude Code session on the machine but act only inside the vault and registered codebases. Headless runs, subagents and `claude -p` scripts are skipped.

Recall puts the partition's open Now lines first, ranked (a `[due::]` date first, soonest first, then the newest date in the line, then owed, waiting, draft) and cut to 240 characters each, and keeps at least a third of its budget (and whatever the Now lines leave) for the latest digests' Outcome, Open questions and Follow-ups sections. Lines that do not fit are counted in one closing line that names `now.py list`.

**"Stop hook error" is not an error.** Claude Code labels every request from a `Stop` hook "Stop hook error:". When the vault asks for a digest, you see `Stop hook error: Foundry memory (not an error): please reply with a short session digest. …`; Claude replies with the digest and the session carries on. The hook never asks twice in a row, and not when Claude's last reply ended with a question to you.

**`/digest`** writes a digest of the work since the last one whenever you want, in any session in scope. The `Stop` hook captures it from the reply; no script or session id is needed.

**Tags.** A note's `tags` are lowercase kebab-case (`api-gateway`), with `/` between the parts of a nested tag (`project/alpha`). `/ingest` lists the partition's tags with `system/scripts/vault_index.py tags --partition <work|personal|shared>` (count, then tag, most used first) and reuses one before inventing a new one. `now` (the Now page) and `rca` (RCA notes) are system tags. `/lint` and the pre-commit hook warn on a tag in another form or a system tag on another note, so a tag you write by hand never stops a sync; the publish gate refuses either when a headless run (`/ingest` or a research Work Order) adds it.

## Machine roles

Each machine that holds the vault has a `machine_role` in its own `system/config.md`, chosen in `/setup`:

| Role | Runs | Use it for |
|---|---|---|
| `standalone` (default) | intake, brief, debrief and smoke check units, and the meetings fetch when enabled; memory hooks; codebases | one machine that does everything |
| `server` | intake, brief, debrief, smoke check and sync units, and the meetings fetch when enabled; memory hooks; codebases | an always-on machine that runs the automation and your coding sessions |
| `client` | nothing automated | reading and editing the vault in Obsidian on another machine |

A server and its clients share the vault through a private `origin` (`remote_mode: private`):

- **Server.** `vault_sync.sh` runs every `sync_interval_minutes` (`foundry-sync.timer`) and before and after every run: it commits headless runs and other changes with scripted messages, merges `origin` and pushes. A run whose note the pre-commit hook refuses stays pending with one `[commit_runs]` alert a day, its note is left out of the sync commit, and the cycle goes on; the daily template update also leaves it out, merges and names it. Network and credential failures never stop the runs; they are alerted once a day until sync works again.
- **Client.** The Obsidian Git plugin commits and syncs every few minutes; `/setup` prints its settings. Write notes in today's briefing between the `#wiki-ingest-start` and `#wiki-ingest-end` markers already in 📝 Notes: the server sends that block to the wiki once, at 05:00 the next morning, so you can edit it all day and the night's sync can bring your last edits over. A block you mark anywhere else in the briefing is compiled within a few minutes. The briefing stays as it is (on every role, blocks stay in the briefing after compiling). Edits that reach the server after 05:00 the next morning are not sent. Files in `raw/inbox/` on a client are not synced. Meeting transcripts dropped into `meetings/drop/<partition>/` are synced, and the server imports them; move a finished file in (an empty one is quarantined). A drop is redacted by the pre-commit hook when it is committed: the file in the folder and the commit both get the redacted text (the same redaction the import applies, with `[REDACTED:…]` in place of each secret), so the raw copy is gone once Obsidian Git commits and the pushed history holds nothing the published transcript does not. Drive links are stripped as the import strips them. A UTF-16 file is rewritten as UTF-8; a file in another encoding is read as UTF-8 with replacement characters, as the import reads it; one that holds NUL bytes once decoded is refused, and the hook names it. The hook also refuses a drop that is a symlink or that has unstaged changes (stage the whole file). Obsidian mobile runs no git hooks, so a drop from a phone is redacted only at import.

### Sync conflicts

A conflict is never resolved automatically. The server aborts the merge, pushes its side to `foundry/server-pending` on `origin`, writes `system/logs/sync-blocked`, alerts once, and skips intake, brief and debrief until it is resolved. Resolve it on the other machine (for `foundry/server-pending`, a client):

```sh
git fetch origin
git merge origin/foundry/server-pending   # a client's own conflict uses origin/foundry/client-pending
# fix the conflicted files, then
git commit
git push
```

On the machine that pushed the pending branch, its side is already checked out: run `git merge origin/<branch>` there instead (`<branch>` is the vault's branch), then resolve, commit and push.

The next server sync clears the marker, deletes the pending branch and starts a brief or debrief that was skipped today.

`wiki/<partition>/Now.md` is the one note both machines write: you tick lines on the client, and the server closes lines on checked evidence. The server rewrites the page only when it closes a line, but a tick on the client next to a line the server just closed can still conflict. Resolve it as above, keeping both changes. The pre-commit hook rejects any file that still holds conflict markers; if a client note that bypassed the hook blocks your commit, the hook names it: fix it, or commit with `--no-verify` knowingly.

## Requirements

The Foundry runs on Arch / Omarchy and on Debian. `system/scripts/check_deps.sh --role <role>` checks what that role needs and prints `pacman` or `apt` install hints:

- `claude` (Claude Code), `git`, `jq`, `flock`, `timeout`
- `python3` 3.11 or newer, with PyYAML (`sudo pacman -S python-yaml`). Missing PyYAML blocks setup.
- `sqlite3` built with FTS5
- systemd user units (`systemctl --user`, `systemd-analyze`). If you want timers to run while you are logged out, enable lingering.
- `bwrap` (bubblewrap) and `socat`: headless runs turn Claude Code's sandbox on, and on Linux it needs both (`socat` carries its network proxy).
- A Google Calendar connector on the Claude account the brief machine is logged in with, for calendar input to the brief. Without it the brief's Sources line shows the calendar as failed. Each morning fetch costs about $0.20.
- A client needs only `claude`, `git`, `jq`, `python3` with PyYAML, and SQLite with FTS5.
- Optional: the tools an enabled extension lists under `deps` (the telemetry extension's ADX sources need `az`), which `check_deps.sh` reports with the extension's name.
- Optional: `herdr` or `tmux` as session backends for sub-project 2
- Development tools, for changing the template (`check_deps.sh` lists them as `dev`): `bats`, `pytest`, `shellcheck`, and the superpowers Claude Code plugin (`/plugin install superpowers@claude-plugins-official`), whose skills run each station in [Development](#development). Without the first three `verify_setup.sh` and `/backup` lint the vault and skip the test suites.
- Obsidian, with the **Dataview** plugin recommended (`wiki/Index.md` dashboards are plain code blocks without it). **[Vault Curate](https://github.com/notoriouslab/vault-curate)** is an optional plugin for link suggestions. It is not a dependency.

## Getting started

Before you start, install what [Requirements](#requirements) lists and sign in to Claude Code (`claude`, then `/login`). For a server or a client, also create an **empty private repository** for your vault on your git host (no README, license or `.gitignore`, so it has no commit of its own to reconcile): that is your private `origin`, and every machine syncs through it.

**First machine (standalone or server).** Clone the template (a repository created from a hosting site's template button shares no history with it, so template updates cannot merge), start Claude Code in it, and paste the prompt below with your answers filled in:

```sh
git clone <template-url> my-vault
cd my-vault
claude
```

**A client.** Set up the first machine first. Then clone your private vault (not the template) and paste the same prompt with `client` as the role:

```sh
git clone <private origin> my-vault
cd my-vault
claude
```

The prompt (replace every `<…>` first; `/setup` asks for any answer still written as `<…>`):

```text
Set up this clone as a new Foundry vault. Run /setup and use these answers; ask me only for what is missing:
- Machine role: <standalone | server | client>
- Brief at <HH:MM>; debrief at <HH:MM>
- Remote: private, origin <private origin URL>   (or: none, standalone only)
- Features: <any of codebases (paths), memory hooks, calendar, meetings, inbox triage,
  Slack notices, Work Orders, template update, extensions (by name); or none>
                                                  (not used on a client)
Never push to the template repository. Before installing units or memory hooks,
show me what will change and wait for my yes. Run any command that needs sudo
(linger) only by giving it to me. When you finish, show the /setup report table
and list what I still have to do by hand.
```

You can also type `/setup` and answer its questions one at a time; the prompt only gives it the answers up front. On a server, `/setup` stops at the units phase until linger is on (`sudo loginctl enable-linger $USER`, which you run yourself). On a client it ends with the Obsidian Git settings to enter and asks you to make one test edit.

`/setup` is idempotent and can be re-run at any time. Its phases (spec §11):

- **0. Role and preflight:** you choose the machine role, then `check_deps.sh --role <role>` lists missing items with install hints. A vault path with a space stops setup (the memory hooks cannot run from it). A client gets no features list and skips phases 3, 6, 6b, 6d, 9, 9a and 11; on a client, phases 5 and 5a only remove units and hooks left from an earlier role, and 6e only links extension skills.
- **1. Existing config:** if `system/config.md` already exists, it is shown and edited, not overwritten.
- **2. Interview:** the brief and debrief times. The timezone is read from the machine; superpowers, the default partition, digest thresholds and the recall budget keep their defaults, and the report says how to change them.
- **2a. Features:** one numbered list of the optional blocks below, with their current state; you pick the ones to set up or change, once. Blocks you do not pick are left as they are.
- **3. Codebases:** you choose repos from a directory scan. Each one is inspected, drafted as `system/codebases/<name>.md` with a partition, and shown to you once to accept or correct.
- **4. Remote:** the template `origin` of a plain clone is renamed `template` for updates, and you choose a private `origin`, no remote, or keep (maintainer mode). A server or client must use a private `origin`; setup checks that git can reach it without a prompt and publishes the branch.
- **5. Units:** the role's systemd units, plus those the features you picked turn on (Work Orders, the template update, meetings, inbox triage), are rendered and enabled on your yes, and you are offered linger (required on a server).
- **5a. Memory hooks:** you are shown the diff to `~/.claude/settings.json` and what each hook does, and it is applied only after an explicit yes. Declining leaves memory off (see [Memory](#memory)).
- **6. Calendar:** one fetch from the Google Calendar connector checks that the brief can read today's events.
- **6b. Meetings and inbox triage:** the meetings partition and your names in action items; the Now page triage writes to; each connector checked.
- **6d. Slack notices:** the channel, and a test message only on your yes.
- **6e. Extensions:** shows each folder under `extensions/` (tracked, and updated with the template), writes the `extensions:` list, each turned-on extension's settings and allow rules, links its skills, and runs its checks. Handoffs to chase is the `handoffs` extension; error telemetry and `/rca` are the `telemetry` extension.
- **7. Index:** the index is rebuilt and the run-commit cutover is recorded (`commit_runs.py --init-cutover`).
- **8. Verify:** `verify_setup.sh --health` runs (lint, then the test suites when the development tools are installed).
- **9. Hand-off:** an onboarding assignment note is created for each codebase.
- **9a. README:** the template's landing page is replaced with your vault's own README.
- **10. Report:** the Obsidian plugins, then a status table of everything that was set up.
- **11. First brief:** `/brief` runs, so you read a brief before setup ends.

Once the units are installed, the timers run real headless `claude -p` jobs. They use your Claude subscription and are capped at 60 runs a day (`HEADLESS_MAX_RUNS_PER_DAY`).

## Security model

- **Headless isolation.** Automation calls `claude` in three ways. `run_headless.sh` runs the vault's own commands; `system/scripts/lib_connector.sh` runs every connector session (calendar, meetings, triage, notices, RCA filing, and extensions' fetches such as handoffs): one connector tool allowed, every other tool denied, `dontAsk`, a fresh directory, a timeout, and a checker that reads the session's tool use afterwards; and the Work Order session (`vaultlib/nightshift_session.py`) runs an approved plan under its own profile (Work Orders, below): the deny list is the profile's `denyRead` plus `CREDENTIALS`, the vault root and every other registered codebase, each entry fencing sandboxed Bash and, as a `Read(...)` rule, the Read tool; the environment is the `session_env()` allowlist of eight variables. `run_headless.sh` runs in restricted mode with a dedicated settings file, no user settings, no user hooks, no MCP servers, no session persistence, a tool list per command, a timeout and a daily run cap. Reads are limited to the vault, writes are limited to the run's staging directory, and Bash runs in Claude Code's sandbox (no network) with sandbox auto-allow turned off, so only allowlisted commands run.
- **Staged publish.** Headless output reaches the wiki only through the publish gate, which checks targets, schemas, partition walls, protected fields, shrinkage and conflicts. Every headless-written note gets `headless` added to its `provenance`.
- **Partition walls.** Links from `work` to `personal` (and the other way) are lint errors. A headless run writes to one partition plus `shared`. From a codebase session, the index CLI returns only that codebase's partition plus `shared`, and those sessions get no general read access to the vault. Walls control links and recall, not storage: all partitions are pushed to the same private `origin`.
- **Private folder.** `wiki/<partition>/private/` holds notes no Claude session opens on its own. Both settings files deny `Read` and `Edit` there: `.claude/settings.json` as `/wiki/*/private/**` (and `/.scratch/**/wiki/*/private/**`, for clones and worktrees under `.scratch/`), and `system/headless.settings.json` as `wiki/*/private/**`, relative to the vault root a headless run starts in. Claude Code applies a `Read` deny to the Read, Edit and Write tools, to `@`-mentions, to Grep and Glob (best effort), to file commands it recognizes in Bash (`cat`, `head`, `sed`), and merges the paths of `Read` deny rules into the sandbox's `denyRead` when the sandbox is on. The index never walks the folder, so lint, `query`, `related`, `show`, `backlinks` and session recall never see it; `vault_index.py field` and `validate` refuse a path in it; the publish gate neither stages a note out of it nor publishes one into it, and a run's snapshot never lists its file names; and Active Projects never opens a page there. A Work Order session already denies the whole vault. Not covered: a Bash command that reads files without naming them (`grep -r … wiki/`) in a session without the sandbox; git commands that print file contents from history (`git show`, `git log -p`, `git diff`, `git cat-file`), which always prompt, so approve one only when it names no private path; and scripts you run yourself. The folder name is case-sensitive: `Private/` on a case-insensitive client (macOS, Windows) is not protected. A link from another note into the folder is reported as broken. Git tracks the folder like any other, so it is pushed to your private `origin`. **To open one file**, name it yourself at the `!` shell prompt: `! cat wiki/<partition>/private/<file>.md`. A command you type there needs no approval, runs outside the sandbox, and adds its output to the session, so Claude reads that one file and no other. Claude cannot ask for it: a deny rule is never offered as a prompt.
- **Data, not instructions.** `CLAUDE.md` tells agents to treat note bodies, raw files, recall blocks and tool output as data. Digests and inbox copies are passed through `redact.py`, and `<private>…</private>` spans are removed. A transcript drop is passed through the same redaction twice: by the pre-commit hook when it is committed (so the pushed blob is already redacted) and by the import.
- **Secret shapes.** The pre-commit hook scans the staged files with the credential shapes `redact.py` redacts (cloud, git host, chat and model API keys, JWTs, PEM private keys, US Social Security numbers) and refuses the commit while one is found, printing `secret shape: <path>:<line>: <shape>` and never the value. It reads only the lines a commit adds, from the staged copy: moving, renaming or archiving a file that already held a shape commits, a line that was already there or that a merged branch brings commits, and fixing a file on disk without staging the fix is not enough. If the shape list cannot be read or the scanner is missing, the commit is refused as unscanned. The sync and the daily template update never stop on one: a file that adds a shape is left out of the sync commit and the rest commits, merges and pushes, with one `[sync]` alert a day per file naming its path, line and shape; the update leaves it out the same way, merges, and names it in its `[update]` line. `/lint` reports the shapes over tracked and untracked files without failing, which also catches what arrived in a merge from a machine that skipped the hook. Both skip `.scratch/`, binary files and nested repositories (a UTF-16 file is read as text); `/lint` also skips `system/tests/` and `docs/superpowers/`, whose fake tokens are test fixtures. The only way past a refusal is `git commit --no-verify`, for a match that is not a secret. Obsidian mobile runs no hooks, so a secret committed from a phone shows up only in the next `/lint`.
- **Write caps.** `lint_vault.sh --staged`, which the pre-commit hook runs, refuses a staged `CLAUDE.md` over 16 KB or `wiki/Index.md` over 8 KB when it is larger than the committed copy (during a merge, the larger of the two sides; a new file counts as empty), printing `<path>:1: error: <size> bytes is over the <cap>-byte cap …`. Shrinking or keeping the size always passes, so a file already over its cap can still be edited and trimmed. The caps are `WRITE_CAPS` in `system/scripts/vaultlib/cli.py`. Only people and merges grow these two files; a refused sync commit stops that sync cycle with its alert until the file shrinks. The Now pages have no write cap, because triage and the brief grow them unattended: `now.py review` reports one over 32 KB.
- **Extensions.** An extension's code runs with the same rules as core's: its connector sessions go through `lib_connector.sh`, its fetches run no model, and its manifest names the credentials it needs, kept outside the vault. Each manifest body states its own data handling (the telemetry extension's masking, for one).
- **User-level changes.** `install_hooks.sh` changes only its own entries in `~/.claude/settings.json` and `~/.claude/commands/digest.md`. It takes a backup first, shows a diff during `/setup`, applies nothing without confirmation, and can be fully reversed with `--uninstall`.
- **Trust dialog.** The first time you open the vault, Claude Code asks whether to trust the folder and lists the permissions `.claude/settings.json` pre-approves: edits under `wiki/`, `briefings/`, `docs/` and `.scratch/`; the vault scripts the commands run (the prep scripts, `now.py`, `lint_vault.sh`, the `vault_index.py` read, rebuild and recall commands, the Work Order queue commands, each enabled extension's `allow` rules (`/setup` phase 6e writes them), `commit_runs.py` and `vault_sync.sh`, `alert.py foreman` (the Foreman's push to you), the `--check` and `--dry-run` forms of the setup scripts, `verify_setup.sh` and the health suite); and the `git` commands `/backup`, `/order` and `/setup` run against the configured remotes (`status`, `add -A`, `commit -m`, a plain `push` or `push -u origin HEAD`, `fetch` from `template`, `remote get-url`, `config user.name` and `user.email`). Still a prompt, by design: `vault_index.py set` (a config change), `git show`, `git log -p`, `git diff` and `git cat-file` (they can print a private note), `install_units.sh` and `install_hooks.sh` without `--dry-run`, `update_template.sh`, `nightshift.py tick`, any push to another remote or with `--force`, every connector write (sending mail or chat, creating events, moving tickets) and every command outside the vault. Those apply to your interactive sessions only; headless runs ignore project settings entirely. Start the Foreman session with the same permission mode as your design sessions (see Work Orders); with the rules above, `acceptEdits` leaves only those boundary prompts, and the Foreman can reach a registered codebase because `/setup` lists it under `additionalDirectories` in `.claude/settings.local.json`. Connector reads a Foreman session uses every day (mail and chat search, calendar reads, ticket lookups) are vault-specific tool names and go in your vault's own copy of the file, above the template block.
- **Gitignored.** `raw/**` contents, `system/quarantine/*`, `system/logs/*`, `system/config.md` (it holds the machine role), `.claude/settings.local.json`, `system/index.db*`, `system/*.lock`, `wiki/.staging/`, `system/jobs/` and Obsidian workspace files.
- **Tracked in your vault, never in the template.** Your vault's `README.md` (the template ships only its landing page), `system/codebases/*.md`, `system/telemetry/*.md`, any vault-only `extensions/<name>/` and the files it reads, and `raw/<partition>/nightshift/*.md` (Work Order queue notes): your vault's own configuration and queue, committed to your private repository so a client's changes reach the server. The template ships only the `example` files. Credentials stay outside the vault (`~/.config/foundry/` and each tool's own login).

## Updating and uninstalling

- **Pull template updates:** `system/scripts/update_template.sh`. Run by hand it refuses to run on a dirty tree; it fetches the `template` remote, merges with `--no-ff`, and stops on conflicts without resolving them. Afterwards it rebuilds the index and re-renders only the units this vault installed. A unit the update adds is listed as `new unit available: <unit>` and left out; read `system/scripts/install_units.sh --dry-run`, then run `system/scripts/install_units.sh` to add it. On a standalone machine or a server, `foundry-update.timer` runs it every morning 45 minutes before the brief (`update_template.sh --unattended`, #87), ahead of the pre-brief units 30 minutes before it (#117) and the smoke check 15 minutes before it, so a fetch the update broke is usually in the alerts before the brief reads them (on a server a long update can still be running then). It waits for `run.lock` and skips the day if another run holds it, commits uncommitted changes first, as the sync does (`commit_runs.py`, then one `sync(<role>)` commit of everything else, half-written notes included), and aborts a conflicted merge (`git merge --abort`), leaving the vault unchanged. A sync commit the pre-commit hook refuses stops the update with the hook's line and nothing is fetched. A published run the hook refuses, and a file that adds a secret shape, do not stop it: they stay uncommitted, the rest commits, the update fetches and merges, and the `[update]` line names them (a refused run points at the same day's `[commit_runs]` alert, which carries the hook's line). If the merge would overwrite one of them, git refuses it and the update fails with the file named. It reports each of those, and a successful update with what it committed and the template pull requests it merged, as an `[update]` line in the alerts the brief reads; the line always lists the commits it made, so a day with nothing new to merge is silent only when there was nothing to commit. On a server the sync runs before and after it. A client gets updates through sync. Rollout: a standalone vault that is dirty every morning is still running the old script, which stops before merging, so run `/backup` once and the next morning's update brings this change. To stop the daily update, run `systemctl --user disable --now foundry-update.timer`; later updates keep it disabled.
- **Your README survives updates:** for its own merge only, `update_template.sh` marks `README.md` `merge=ours` and defines that driver (`git -c core.attributesFile=… -c merge.ours.driver=true merge`). A README your vault has changed keeps your version, on the first update too; one you never edited takes the template's landing page. Sync merges between your machines define no driver, so a README edited on two machines conflicts as usual and nothing is lost. `/setup` writes a starting README while yours is still the landing page.
- **The first update with the briefing archive:** the first brief after it moves every briefing older than yesterday into `briefings/archive/`, and the next sync lints them all, so run `system/scripts/lint_vault.sh` before updating and fix what it reports.
- **Update the humanizer skill:** `.claude/skills/humanizer/` is humanizer v3.0.0, copied unchanged with its MIT license. To move to a newer version, copy the new `SKILL.md` and `LICENSE` over it by hand in the template repo, then update the version and checksum in `system/tests/vault_integrity.bats` and the version in this manual. Vaults receive it through `update_template.sh`.
- **Update the grilling skill:** `.claude/skills/grilling/` is `grilling` from mattpocock-skills 1.2.3 with its MIT license, unchanged above its `<!-- Foundry addition` line; the Foundry's idea questions sit below it. To move to a newer version, copy the new upstream text over the part above that line and the new `LICENSE` over the old one, then update both checksums in `system/tests/vault_integrity.bats` and the version in this manual.
- **Remove systemd units:** `system/scripts/install_units.sh --uninstall` removes only units whose header names this vault.
- **Remove memory hooks:** `system/scripts/install_hooks.sh --uninstall` removes only the entries owned by this vault, any container the install had to create, and the owned `/digest` command. It still works if the hook files are gone.

Both installers also accept `--dry-run`.

## Architecture

The Foundry is a **gated LLM-wiki compiler**. It composes an LLM-compiled markdown wiki (raw sources the model reads; summary, entity and concept notes it writes; a schema per note type; ingest, query and lint over an index), fixed workflows with a deterministic check after each model step, and a model treated as untrusted, with policy kept in code. It extends the LLM wiki in three ways: a **deterministic publish gate** between the model and the vault (staging, schemas, walls, conflict and shrink checks, all-or-nothing apply); **partition walls** (`work`, `personal`, `shared`, `private/`); and **scheduled headless runs with an operations layer** (brief, debrief, Now, Work Orders, notices) on systemd timers under one lock. The program that moves every feature onto shared parts is the [factory plan](docs/superpowers/2026-10-21-factory-plan.md).

```
sources ──confined fetch (1 tool + checker)──► raw/  (audit log, never edited)
                                                 │
                              intake (scripts: convert, redact, route)
                                                 │
                         headless claude ──► wiki/.staging/<run>/
                                                 │
                          publish gate (deterministic, all-or-nothing)
                                                 │
        wiki/ · Now · briefings ──► index ──► /query · brief · recall · notices
```

**Blueprints.** Every feature has one of four shapes; its spec names which.
- **Source**: confined fetch → check → parse → cursor → route (Now, alerts, brief, inbox). Parts: a `lib_connector.sh` session with one tool, a checker that reads the session's tool use, a cursor, `now.add` for Now lines, `redact` for outside text, a smoke row, a unit and its alert tags. F1 moves the checker and the fetch helpers into shared libraries. Triage, calendar, meetings, handoffs, the intraday watch, notify.
- **Poller**: HTTP fetch with no model → store → route. Parts: a source's cursor, alerts and unit, and no `claude` session. Telemetry.
- **Compile run**: headless session → `wiki/.staging/<run>/` → publish gate. Parts: `run_headless.sh` (restricted settings, a timeout, the daily cap, `run.lock`), staging and `publish.py`. Ingest, brief, debrief, research.
- **Work Order**: plan-then-execute in a sandboxed session → pull request or findings note. Parts: an approved plan that passes the readiness check, the runner's sealed profile (`system/nightshift/*.settings.json`).

**Principles.** Each is what the code does today, with where it is enforced; "prose only" marks a rule no test holds.

| # | Principle | Enforced in |
|---|---|---|
| P1 | **Scripts do the exact work**: fetching, parsing, dedupe, routing, dates and counts are code; the model does judgment. | Prose only (What The Foundry is); each feature's tests |
| P2 | **Every model write passes the gate**: a headless run writes only to staging, and the gate checks and applies all or nothing. | `run_headless.sh`, `headless.bats`; `vaultlib/publish.py`, `test_publish.py` |
| P3 | **Untrusted input gets one tool and a checker**, and the checker's verdict wins. | `lib_connector.sh`, `lib_confine.sh`, `connector.bats`; each source's checker |
| P4 | **Content is data**: notes, mail, chat and recall never authorize an action. | The recall label (`vaultlib/recall.py`), the Work Order contract, `vault_integrity.bats`; agent behaviour is prose only |
| P5 | **Walls hold at every step**: partitions and `private/` hold at the gate, in the index and in each session's read set. | `vaultlib/publish.py`, `vaultlib/index.py`, `test_index_rules.py`, the settings deny rules |
| P6 | **Raw is append-only, notes are never deleted**: compiled notes are deprecated or superseded. | The gate has no delete decision (`vaultlib/publish.py`); the rule is prose only (CLAUDE.md Lifecycle) |
| P7 | **One schema per note type**, checked at the gate and in lint. | `vaultlib/schema.py`, `vaultlib/publish.py`, `vault_integrity.bats` |
| P8 | **Atomic writes under one lock**: writes are atomic or journaled, and runs that touch the vault serialize on `run.lock`. | `vaultlib/publish.py`, `now.py`, `run_headless.sh`, `headless.bats` |
| P9 | **A small, budgeted core**: features are extensions that plug in through their manifest. | `vault_integrity.bats` (core line budget, schema count, vendor names) |
| P10 | **Fail loud with a reason**: three exit codes; a failed source alerts once with its class; a check that cannot run says so. | Working rules (prose only); `vaultlib/alerts.py`; connector health |

**Known departures.** Each is a roadmap fix in the factory plan.

| # | Departure | Fix | Phase |
|---|---|---|---|
| D1 | Interactive sessions skip the gate: `.claude/settings.json` allows `Edit(/wiki/**)`. | Gate interactive wiki edits | F5 (#310) |
| D2 | Triage, the intraday watch and the today log write model-derived Now lines and the today file through their own scripts, outside the gate. | Give machine writers the gate's checks | F5 (#310) |
| D3 | Core names extension features: alert tags, the `production_error` route, index and schema rules. | Move them into each extension's manifest | F2 (#307) |
| D4 | Extensions import core internals. | A named extension API; nothing else imported | F2 (#307) |
| D5 | The core budget counts only `system/scripts`, not `system/hooks` or `.claude/commands`. | Count them too, at a measured cap | F3 (#308) |

## Development

Work follows the superpowers pipeline. Each station has its skill and leaves a record:

| Station | Skill | Record |
|---|---|---|
| Grill (an idea the owner proposes) | `/grilling`: is it worth building, for whom, what happens without it, its smallest version, what it displaces | the decisions on the idea's issue, or a `## Grill` section in the spec |
| Spec | `superpowers:brainstorming`, ending with its builder check (`builder-check-prompt.md`) | `<date>-<topic>-design.md` in [`docs/superpowers/specs/`](docs/superpowers/specs/) |
| Plan | `superpowers:writing-plans` | `<date>-<topic>.md` in [`docs/superpowers/plans/`](docs/superpowers/plans/) |
| Build | `superpowers:subagent-driven-development` or `superpowers:executing-plans`, with `superpowers:test-driven-development` | commits, one task each |
| Review | `superpowers:requesting-code-review` (and `foundry-review` once the factory's F4 ships it) | findings fixed before merge |
| Close | `superpowers:verification-before-completion`, `superpowers:finishing-a-development-branch` | the gate green, the roadmap row updated |

An idea that comes from an audit finding, an issue a live vault logged, or a review is not an owner idea: its spec's Grill line names that source instead. A feature names its blueprint in its spec ([Architecture](#architecture)) and is built from the standard parts. Spike results go in [`docs/superpowers/spikes/`](docs/superpowers/spikes/). Every finding from the design reviews is traced in spec §13.

**Required header lines.** `system/tests/conformance.bats` fails a spec or plan dated 2026-10-21 or later that lacks them (research briefs excepted); older ones are grandfathered by the date in their file name.
- A spec: `**Grill:**` (the date and where the decisions are recorded, as an issue URL or a `## Grill` section in the spec or in the file its `**Program:**` line names, or `not an owner idea: <source>`), `**Builder check:**` (the date, the questions found and how each was settled), `**Blueprint:**` (Source, Poller, Compile run, Work Order, or `none: <why>`).
- A plan: the writing-plans header (`REQUIRED SUB-SKILL`), `## Global Constraints`, `## Review Focus`, and a `**Spec:**` line naming its spec.

**Two lanes.** That pipeline is the feature lane. A fix takes the fast lane and skips the grill, the spec and the plan. A fix is a change whose scope is clear from one sentence, with one failing test that passes after the change and the gate green, that touches none of the safety surfaces: permissions and settings files, the sandbox, the publish gate, redaction, and new note types. A fix that edits the `ingest`, `brief` or `debrief` command text also re-runs the live acceptance steps (below). It ships as a pull request whose body is the issue line or review finding it fixes and the name of its test, and which carries one `defect:` label for the class it fixes: `defect:C1-too-large` (tool result too large, page caps), `defect:C2-now-line`, `defect:C3-timeout`, `defect:C4-confinement`, `defect:C5-alerts` (routing, alert-once), `defect:C6-race`, `defect:C7-redaction`, `defect:C8-names` (names leaking), `defect:C9-extension` (manifest and loader gaps), `defect:C10-flaky-test` (tests that skip or flake), `defect:C11-input-bounds` (encoding, input bounds), `defect:C12-stale-docs`, `defect:C13-changelog` (CHANGELOG conflicts), `defect:C14-gate-escape` (a write that escapes the publish gate or a session's confinement path). A class that recurs after its gate exists means the gate is wrong. A fix may run as a Work Order: the readiness check reads the plan from a file committed at the Work Order's base, so it then needs a short plan file with its `### Task N:` list. A fix that grows past its sentence, or draws a design question in review, stops and becomes a feature; the default when in doubt is the feature lane.

**Keeping it quick.** These rules trim the feature lane; bring the stricter ones back if problems appear.
- **Probe first:** a spec that relies on an outside tool or API calls it once (in a throwaway directory) and records what came back before the design settles.
- **Docs tests check names:** a test on FOUNDRY.md or a command file checks that a key, command or heading is there, not its exact wording.
- **CI is the gate:** a pull request's gate is CI's `gate` check. Run `verify_setup.sh` locally after a change to `run_headless.sh`, the settings files or the systemd units, or to reproduce a CI failure; each task still runs its own suites with `system/scripts/test.sh`.
- **Small features skip the plan:** a feature under about 300 lines that touches no safety surface ends its spec with the task list instead of a separate plan, and one reviewer checks the finished branch.
- **Safe features merge themselves:** such a feature auto-merges once CI and the reviewer pass. A change to a safety surface, to connector confinement or to the Work Order runner waits for the owner's merge.

**Working rules.** These hold in both lanes.
- Report or record an action only after reading its command's status, and say what you could not verify.
- Every rule that adds rows, lines or findings ships with the rule that removes them.
- No fix without its cause written down first; a cause not established is written as not established.
- Answer it before asking it: check the files, the config and the git log before a question goes to the owner.
- A negative result is not evidence unless the instrument could have returned a positive; name the missing instrument.
- Three exit codes everywhere: 0 clean, 1 findings, 2 could not run; never collapse 2 into "empty".
- The reviewer re-runs the gate off its own run before reading the implementer's report.
- Seed a proving test from the hazard, never from the writer's own output.
- The writer goes through what the reader goes through: one frontmatter composer.
- Ship the activation story: how a tool or rule is triggered, and where, is part of delivering it.
- Quote chat and mail verbatim, attributed, hedges intact; your own read goes on a separate marked line.
- A retired load-bearing claim leaves one marker: `superseded <date>, was "<old claim>"`.
- Verify before you destroy: uncommitted work or an unfiled action stops a delete.
- No colleague's name in a commit message; write the fact or point at the record.
- A hook that fires on every tool call fails open and resolves its root from `BASH_SOURCE`, never `$HOME`.

**Release notes.** A pull request that changes something a vault user would notice adds its line to `CHANGELOG.md`, under today's date in **Changes**, in plain words, ending with its PR number: `- <what changed> (#<n>)`. When a vault must do something, an indented `  - Action: <what to run>` line follows. Docs, test and CI changes add none. A Work Order's plan adds the line in its last task. The morning update shows the lines it merged in the brief's What changed.

The gating suites must pass at the end of every task. Install the development tools first (`bats`, `pytest`, `shellcheck`, and optionally `parallel` (GNU) and `pytest-xdist`): without the first two the gate lints only and prints `SKIP suites` in its summary. The gate runs the bats suites side by side when GNU `parallel` is installed and spreads pytest over every core when `pytest-xdist` is. In the template repository, CI runs the same gate on every pull request. A test that needs what the machine lacks (a user systemd instance, `bwrap`, a non-root user) skips with `environment:` in its reason; `--require-suites`, which CI and `verify_on_host.sh` pass, fails it instead. One command runs them all and exits non-zero if any fails:

```sh
system/scripts/verify_setup.sh            # lint, every system/tests/*.bats except system_health.bats, then pytest
system/scripts/verify_setup.sh --health   # also the advisory live-state suite
```

One suite or one pytest target runs through `system/scripts/test.sh <suite.bats | pytest path> [args…]`, which sets the gate's environment (temp files under `.scratch/tmp`, a git ceiling) so no command needs a leading `TMPDIR=` assignment. Plans name it in their test steps.

`vault_integrity.bats` fails when a tracked template file holds a name from your forbidden-names list, kept outside the repository at `$FOUNDRY_FORBIDDEN_NAMES` (default `~/.config/foundry/forbidden-names`, one case-insensitive name per line, `#` comments); it reports `<path>:<line>` and the list line, never the name, and skips when the list is absent or the checkout is a vault. CI reads the list from the Actions secret `FOUNDRY_FORBIDDEN_NAMES_LIST`, written to a file before the gate.

**Permissions while developing.** The template's `.claude/settings.json` allows only the read-only vault commands, because vaults merge it (fewer-prompts spec). Development commands go in `.claude/settings.local.json` (gitignored; "Yes, and don't ask again" writes there too), for example:

```json
{"permissions": {"defaultMode": "acceptEdits", "allow": [
  "Bash(system/scripts/test.sh *)", "Bash(system/scripts/verify_setup.sh*)", "Bash(shellcheck *)",
  "Bash(git status*)", "Bash(git diff*)", "Bash(git log*)", "Bash(git show*)", "Bash(git fetch *)",
  "Bash(git add *)", "Bash(git commit *)", "Bash(git checkout -b *)", "Bash(git switch *)",
  "Bash(mkdir -p .scratch*)"]}}
```

A rule matches one plain command: a leading assignment other than a few known-safe variables, a `&&` chain, a loop or a redirect each draw a prompt again, which is why `CLAUDE.md`'s Bash line forbids them and why `test.sh` exists. The `auto` permission mode (a classifier approves routine calls) is honoured only in `~/.claude/settings.json` or on the command line (`claude --permission-mode auto`); a project or local file silently ignores it. An approved plan needs no prompts at all when it runs as a Work Order (`/order add`): the session runs with `--permission-mode dontAsk` and a fixed tool list.

`system/tests/system_health.bats` checks live service state and is advisory only. To prove the suite on Debian, run `system/tests/verify_on_host.sh <ssh-host>`: it copies the committed tree to a temporary directory on that host, runs the gate there, and exits with its code. The host needs the `apt` packages `check_deps.sh` lists, its `dev` tools included: the script runs `verify_setup.sh --require-suites`, which fails rather than skip the suites. After any change to `run_headless.sh` or the settings files, re-run the spike checklist (spec §7.4) by hand. After any change to `run_headless.sh`, `system/headless.settings.json` or the `ingest`, `brief` or `debrief` commands, re-run the live acceptance steps (Plan 4a, Task 9) in a throwaway clone. After a change to `lib_connector.sh` or a `claude` version change, one `system/scripts/calendar_fetch.sh` run from a throwaway clone proves the connector flags: that file is the one place they live. On a live vault a `[smoke] version` alert is the trigger: the daily smoke check records the version in `system/logs/claude.version` and reports a change once.

**Ingest evals.** `system/scripts/eval_ingest.sh [--case <name>]… [--runs N] [--max-usd D] [--local]` runs the golden cases in `system/tests/golden/ingest/` through one real intake tick each, N times (default 3), in a throwaway copy of the fixture vault, with the `claude` the units use. `system/scripts/eval_check.py` scores each run with fixed checks on its records and the published vault; no model grades a run. A safety case (the walls, the inbox injection, the no-shrink cases, shared placement) must pass every run, a quality case two of three. The run stops at `--max-usd` (default 5) and records the rest `skipped (budget)`. Each run is a line in `system/logs/evals/ingest-<YYYY-MM>.jsonl`, and the summary prints a pass rate and the mean cost per run for each case. Evals are not gating: run them after a change to the `ingest` command, `run_headless.sh`, the headless settings, the intake's staging (conversion, redaction) or the `claude` version, and record the result with the live acceptance re-run. A case built from your own notes goes in `system/tests/golden/local/` (gitignored; `--local` runs it). Every new Workcell ships with at least one eval case.
